# meow-starter 可靠性与可扩展性加固设计

## 1. 背景

`meow-starter` 已经具备 Tauri 2、Vue 3、SQLite、系统托盘、自动更新、设计系统，以及 Agent、MCP、本地推理的模块骨架。本轮工作不重写现有架构，也不拆分 Monorepo；目标是在现有单仓和模块契约上，让已经公开承诺的能力可运行、可测试、可解释。

## 2. 第一性目标

项目的长期目标按以下顺序决策：

1. **轻量化**：默认启动与默认发行物只承担核心能力；未启用模块不执行、不进入首屏加载路径。安装依赖与发行物体积必须使用可测量数据描述，不使用无法验证的“零依赖、零体积”。
2. **高扩展性**：每个能力有单一职责、显式依赖、稳定接口和独立测试；新增能力不需要理解整个项目。
3. **高可玩性**：主题、Provider、Tool、Hook、MCP 等扩展点保留，但只有跑通最小闭环的能力才标记为可用。
4. **易于上手**：开发者或 Agent 可以从一份入口文档找到配置、代码、权限和验证命令；错误必须说明缺少的配置和修复方法。
5. **安全默认**：密钥不离开 Rust 可信边界；WebView 不读取明文密钥；网络目标、权限和危险工具必须显式约束。

## 3. 非目标

本轮不做以下工作：

- 不拆分 `core`、`agent`、`mcp` 为独立 npm/Cargo 包。
- 不实现 `create-meow-app` 项目生成器。
- 不实现 Pi sidecar、RAG、STT、TTS、OCR 或插件市场。
- 不为了“完全可选依赖”引入自定义构建系统。
- 不承诺未在真实工具链中验证的 Android、iOS、签名或自动更新能力。

## 4. 成熟度模型

README 与文档统一使用四级状态：

| 状态 | 定义 |
| --- | --- |
| Stable | 默认路径有自动测试，主分支持续通过，错误处理与文档完整 |
| Beta | 核心路径已实现并有自动测试，但仍缺真实多平台或发布验证 |
| Preview | 接口与骨架可使用，尚未形成完整端到端验证 |
| Roadmap | 只有设计或规划，不作为当前功能宣传 |

初始目标状态：

- Stable：Vue/Tauri 默认桌面底座、主题、SQLite 示例、桌面托盘、默认 CI。
- Beta：自动更新代码路径、移动端响应式布局。
- Preview：Agent、Ollama、MCP、可选系统插件。
- Roadmap：Pi sidecar、RAG、STT/TTS、OCR。

## 5. 阶段设计

### 5.1 阶段一：可信基础

保留 `src/modules` 契约，修复已经影响默认体验的问题：

- 使用可被 Vite 构建分析的 Icon 注册方式，生产环境不再依赖 `@vite-ignore` 裸模块路径。
- 修正移动端外壳布局，使底部导航位于内容区下方，并覆盖安全区域。
- Updater 在默认占位端点下显示“未配置”，不发起无意义请求。
- 浏览器 mock 数据层保持同一内存实例，行为与文档一致。
- 明确“动态加载”只表示不进入首屏执行路径，不再等同于安装依赖或发行物为零。
- 为模块拓扑、平台判断、Updater 配置和内存存储建立单元测试。

### 5.2 阶段二：安全 Agent 最小闭环

Agent 保持现有 `AgentRuntime`、Provider、Tool、Hook 等公开契约，内部数据流调整为：

```text
Vue WebView
  -> providerId + model + messages
Rust Agent Gateway
  -> Provider allowlist
  -> OS Keychain
  -> 固定 Provider endpoint
  -> 流式 Channel
Vue WebView
```

安全约束：

- 移除前端读取明文密钥的公开命令。
- 前端不能传任意鉴权 Header 名；云端 Provider 使用 Rust 固定映射。
- 自定义 OpenAI-compatible 服务必须显式配置；默认只允许回环地址用于本地推理。
- 请求设置连接、总时长和响应大小限制；返回错误经过截断和脱敏。
- CSP 默认启用，开发和生产策略分开。

功能闭环：

- `loadAgent(config)` 自动注册 `config.providers`。
- ChatPanel 发送历史消息而不是只发送最后一条 prompt。
- SQLite memory store 参与会话恢复。
- Tool 审批默认拒绝；只有显式处理器批准后执行。
- MCP 工具经过适配后进入同一审批与 Hook 边界。

### 5.3 阶段三：CI 与发布可信度

CI 增加以下门禁：

- TypeScript 类型检查、Vite 构建、单元测试。
- Rust `fmt`、`clippy`、默认 feature 和 `--all-features` 检查。
- 可选 feature 的代表性组合检查。
- Markdown 相对链接检查。
- README 中版本号、功能状态和配置占位符检查。

发布工作流增加：

- Git tag、`package.json`、`Cargo.toml`、`tauri.conf.json` 版本一致性检查。
- Updater endpoint、更新公钥和签名 Secret 预检。
- 未签名构建必须明确标记，不能描述为可直接分发。

真实签名、公证、移动端商店发布依赖外部账号和密钥，不作为本地完成条件。

### 5.4 阶段四：README 视觉统一

代码和文档验证完成后再更新视觉资产，避免图片展示不存在的能力。

- `docs/preview.png`：使用生图模型制作桌面端产品展示图，界面内容以验证后的实际功能为准。
- `docs/mobile-concept.png`：使用生图模型制作移动端产品展示图，保持与桌面图同一品牌语言。
- `docs/cross-platform.png`：使用生图模型制作五端生态概念图，不在图片内承载复杂说明文字。
- `docs/architecture.svg`：使用确定性 SVG 重绘精确组件、依赖和数据流；视觉语言与三张位图一致。

图片统一约束：清爽、轻量、技术感、避免紫色 AI 渐变、避免虚假功能、避免模型生成大段文字、保留 README 深浅背景下的可读性。

## 6. 错误处理原则

- 配置缺失：指出缺失字段、文件位置和修复动作。
- 能力未编译：指出对应 Cargo feature 和 capability 权限。
- 平台不支持：安全降级，不调用后端命令。
- 网络失败：区分未配置、连接失败、鉴权失败、限流和 Provider 错误。
- Agent 工具拒绝：返回结构化拒绝结果，不执行工具副作用。
- UI 启动失败：模块装配错误必须可见，不能留下未挂载的空白窗口。

## 7. 测试与验收

每个阶段使用测试驱动开发：先提交失败测试，再写最小实现，再重构。阶段完成必须满足：

1. 新增测试覆盖本阶段的核心行为和至少一个失败路径。
2. `npm run typecheck`、`npm run build`、前端测试全部通过。
3. Rust 格式、静态检查和对应 feature 构建通过。
4. 默认桌面体验没有回归。
5. README 的能力状态与验证证据一致。
6. `git diff` 中不存在密钥、生成目录、构建产物或无关改动。

## 8. 实施顺序

严格按以下顺序执行：

1. 测试基线与可信基础。
2. 安全 Agent 最小闭环。
3. CI、发布预检和文档状态。
4. README 视觉资产。
5. 全量验证与发布建议。

前一阶段未通过验收，不进入下一阶段。
